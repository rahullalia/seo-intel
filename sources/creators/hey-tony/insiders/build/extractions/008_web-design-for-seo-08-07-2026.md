# Web Design for SEO — 08.07.2026 (Leanne Jones, Leanne Digital)

## Tactics & step-by-step how-to
- Blog post anatomy — three "must include" elements up top: title, author, date — then a full-width featured image to visually break the page, then body copy in a centered column.
- Set the body-copy container to a **max-width of 940–1,000px** — never span edge-to-edge. Demoed live on Huckberry: removed the max-width constraint on a real post to show the readability drop, then reverted it.
- Line-height workflow: inspect via DevTools, then dial in. Tested live at 0.8 (very hard to read) → 1.2 ("a little bit better") → 1.8 (target value, "almost 2x," easiest to read).
- Background "white" tactic: pick a near-white, not pure white — check the hex code. Too much gray reads as "muddy"; true-white-adjacent reads as clean/subtle.
- Paragraph spacing: use generous margin-top/margin-bottom between paragraphs (shows as an orange highlight in DevTools inspect) — gives the eye a visual break and improves scannability.
- Font-pairing method: get creative/fancy with the **headline font** (readability cost is low since headline text is big and short); keep the **body font** simple (sans-serif or serif) and different enough from the headline font that the two don't visually compete for hierarchy.
- Mobile adaptation: font size can shrink slightly vs. desktop because the screen sits closer to the eyes (Huckberry's live CSS: 17.5px desktop → 16px under a ~720px breakpoint) — but keep side margins/padding generous regardless, so text never crowds the edge.
- Color hierarchy trick: darker color for headlines, lighter gray for body copy — the contrast between the two creates hierarchy without adding any new elements.
- Homepage build order (standard wireframe, presented as the default starting point for most businesses): hero image → trust-building elements → introduce yourself → highlight products/services → testimonials → explain your process → FAQs → final CTA. Put a CTA at the very top of the page and again at the very bottom of every page.
- Left-align long-form body copy; reserve centered alignment for titles and short text blocks. Demoed centering a full paragraph live to show the readability drop.
- Break up blog body copy with large images, pull quotes, lists, and tables so posts don't read as one dense wall of text — reduces the feeling of being overwhelmed and keeps people scrolling instead of bouncing.
- Justified text: only use it if, in your specific font/column width, you don't see "rivers" (odd vertical gaps of whitespace running down the paragraph) — harder to control on responsive web layouts than in fixed print.
- Hero images: size at **1440×720px** and export as **WebP** (next-gen format) so a large, full-impact hero doesn't tank load speed.
- Don't put sliders or autoplay video at the top of a page — these hurt load speed far more than one correctly sized/optimized static hero image.
- Logo file handling: use SVG where possible; a PNG works as long as its background is transparent (not a white box) — set the nav bar itself to transparent when it sits over a hero image.
- Fixing an overloaded nav: shorten/rename dropdown sub-items to be specific rather than categorical (e.g., a "Cityscapes" dropdown item renamed to the actual city, "Amsterdam"), install a mega-menu plugin to handle a large number of dropdown items cleanly, and move secondary links (social icons, etc.) out of the top nav into a bigger footer menu.
- Fixing a duplicate-H1 problem: identify which heading is the true page-level H1 (usually the title the theme/template outputs) and strip any second H1 sitting in the post body — this also cleans up the visual hierarchy automatically.
- Fixing wrong heading levels inside a locked page builder (e.g., a platform auto-pulling a body H2 as an oversized "category" headline): where the tag itself can't be changed directly, wrap the specific snippet in inline HTML — `<span style="font-size: 30px">...</span>` — or ask ChatGPT to generate the custom HTML/CSS needed.
- Elementor-specific: build a custom blog/archive template in **Theme Builder**, assign it to the blog post/blog-roll page, and every new post auto-formats into that template.
- If the platform allows a custom excerpt length, truncate the auto-pulled snippet to a fixed character count (~200 characters given as the example) instead of letting it pull a raw heading + paragraph fragment.
- To promote a YouTube channel without cluttering the top nav: build a small custom sidebar callout graphic instead (can ask ChatGPT to generate the image), and hyperlink the whole graphic to the channel.
- Naming the blog page itself doesn't need SEO effort — "Blog" or "Insights" is fine; Google understands the convention and the roll isn't the page you're trying to rank anyway.

## Rules / dos & don'ts
- Never set body font below 16px, on any device.
- Content column: 940–1,000px max-width — never full-bleed edge to edge.
- Line-height target for body copy: ~1.8.
- Desktop font can run larger than mobile (example: 17.5px desktop / 16px mobile at <720px breakpoint) — but the desktop/mobile gap should never come at the cost of mobile spacing.
- Never use pure black for body copy — use a soft/dark gray instead; pure black reads as "jarring" next to softened text.
- Never center-align large blocks of body copy — left-align it.
- Justified text is conditional, not banned outright — allowed only if it isn't visibly creating rivers.
- Every section should have a CTA, but the goal is ease-of-access, not maximum CTA count — a busy background graphic behind a CTA/headline can make it harder to read, which defeats the purpose.
- One H1 per page, period — a duplicated/competing H1 is a hierarchy bug to fix, not a styling choice.
- Font-weight 700 for a link that needs to visually pop/read as bold.
- Blog roll/archive pages are optimized for usability, not ranking — don't spend ranking effort there; the individual post is the page expected to earn traffic.
- Keep top nav to primary destinations only; social icons and secondary links belong in the footer, which can hold far more items without feeling cluttered.

## Tradeoffs & nuance
- Fancy/complex fonts cost little readability on headlines (short, large text) but actively hurt readability on body copy (long stretches, more visual noise) — hence "creative on headline, simple on body," not a blanket rule against decorative fonts.
- Justified text is a real style option, not an automatic mistake — the actual risk (rivers) is font/column-width dependent and harder to manage on responsive web layouts than in fixed print, so the rule is "check for rivers," not "never justify."
- Mobile font size can legitimately shrink versus desktop (screen-proximity argument), but that's the one thing allowed to shrink — spacing/margins should stay generous regardless of screen size.
- A confident brand can override the "standard" layout once it knows itself (Medium's oversized-title variant cited as proof) — the standard wireframe is a safe starting baseline, not a ceiling on creativity.
- A design can feel "minimal" while still having a lot of visual elements present — the minimal *feeling* mostly comes from generous white space, not from removing content.
- Page-speed risk is concentrated in a few specific choices (sliders, autoplay video, unoptimized image formats/sizes) rather than image count in general — one large, correctly sized/optimized (WebP) hero image is a fine trade for visual impact.
- Platform choice is a real constraint on design control, not just a preference: Elementor's Theme Builder gives near-full template flexibility, while Kadence Blocks, Kajabi, and SmugMug each imposed a real limitation on this call (unclear pattern-application flow, wrong auto-generated heading levels, restricted column/layout options) that had to be routed around with inline HTML/CSS, ChatGPT-generated snippets, or raw HTML blocks rather than solved with a clean native setting.
- Heading-hierarchy bugs recur across totally different platforms and skill levels (Spoon's duplicate H1, Kelly's Kajabi heading, Stephanie's unclear Kadence pattern) — suggesting this is a common blind spot for non-developers self-building on visual page builders, not a one-off mistake.
