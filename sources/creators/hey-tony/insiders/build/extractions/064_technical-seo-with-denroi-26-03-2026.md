## Tactics & step-by-step how-to

- **Speed triage when choosing between fixing a current template vs. switching to a new one:**
  - Run a speed test (PageSpeed Insights or the hey Tony audit tool) on the current template AND the candidate new template before deciding where to spend effort.
  - Priority order after testing: set up a CDN → optimize files (compression, file type) → review hosting.
- **Checking robots.txt directly:** go to the homepage URL and append `/robots.txt` (e.g. `yoursite.com/robots.txt`) to view the live file.
- **Fixing Shopify robots.txt over-blocking:** open the Shopify robots.txt, remove "disallow" lines for blog, collections, products; these are commonly injected by a third-party app/plugin rather than done manually. Disable the suspect plugin, wait a few minutes for cache to clear, then recheck the `/robots.txt` URL.
- **Fixing a wrong/missing H1 on Shopify:** go to Online Store → Edit Code → open `theme.liquid`, search near the page title code, change the wrong heading tag (e.g. H3) to H1. Alternatively, ask Shopify's built-in "Sidekick" AI assistant to help set the H1 on the homepage.
- **Fixing scrambled heading order (H2/H3/H4 out of sequence, cart/footer elements tagged as headings):** go through the page's headings one by one and correct each tag to the right semantic level/order (one H1, then properly nested H2s/H3s); on a very old, many-times-updated theme it may be faster to rebuild the page than patch it.
- **Sanity-checking a tool's word count before trusting it (e.g., vs. a competitor):** don't rely on the tool's number if it looks inflated — manually highlight all visible on-page content and paste into a separate word/character counter, and do the same for the competitor's page for a fair comparison. Known inflation sources: pop-ups, review-widget text, hidden/background code, mobile-version content counted twice, currency/country selector text.
- **Diagnosing a bot being blocked on a full-site crawl (but not on single-page checks):** check both `.htaccess` and `robots.txt` for user-agent blocks; specifically check whether "Python" is being blocked (many SEO audit tools, including hey Tony's, run on Python as their crawler mechanism) — remove it from the block list and retest.
- **Diagnosing/fixing a CDN blocking a legitimate audit-tool crawler:** identify the CDN in use (e.g. via the BuiltWith browser extension), then get hey Tony's crawler whitelist (IP/user-agent list — held by Matt) added to that CDN's/firewall's allowlist so the crawl isn't blocked.
- **Live site-speed audit checklist (as run on Jonathan's site):** confirm a caching plugin is active (SiteGround Speed Optimizer / WP Rocket) → confirm PHP version is current (8.2.30 = fine) → confirm images are served as WebP → confirm whether JavaScript is delayed → pull a PageSpeed Insights report and identify which scripts are slow/badly ordered.
- **Converting images to WebP:** don't rely on a plugin to auto-convert on the fly — upload images already saved as WebP for best results. On platforms without server/hosting access (e.g. Wix), use any online JPEG/PNG-to-WebP converter, or in Photoshop go File → Save As → change the file-type dropdown to WebP, then re-upload the same file (visual quality unchanged, only file size/type changes).
- **Delaying JavaScript for speed:** from the PageSpeed report, identify the specific long-rendering scripts, enable "delay JavaScript" for those specifically in your caching/optimization settings (e.g. WP Rocket or SiteGround settings), then re-test — check both the speed gain and that nothing broke, since load order can matter (something delayed may be a dependency another script needs first).
- **Getting precise plugin/settings guidance from an LLM:** use Gemini or ChatGPT (or any LLM); if the generic answer doesn't match your specific host's dashboard, screenshot your own settings screen and attach it for context.
- **Local business schema for a multi-city service-area business:** put the main schema (matching the Google Business Profile) on the homepage, listing every service-area city. Add a separate, page-specific schema on each individual city/location page mentioning only that one city. If you run multiple separate Google Business Profiles (multiple physical locations), you need a full separate schema per profile/location.
- **Checking true indexing status of a URL:** paste the exact URL into the URL Inspection bar at the top of Google Search Console. "URL is on Google" + green checkmark = indexed. "Page is not on Google" = not indexed (demoed live on a 404 page, which correctly showed not-indexed since there's no content).
- **Diagnosing "page with redirect" / not-indexed errors in GSC Page Indexing:** open the flagged URL and check whether it silently appends a parameter or redirects (e.g., a city name got appended to the end of the URL) — the redirected/parameterized version won't rank, but the clean target URL will (check that one separately via URL Inspection).
- **Diagnosing www/https mismatches feeding "page with redirect" errors post-migration:** compare the protocol (http vs. https) and www vs. non-www format of each flagged URL against the site's actual live/canonical format — mismatches from a redesign are common; correct ones can be ignored, real mismatches should be fixed.
- **If a flagged URL is identical to the live URL with no added parameter:** treat it as a Search Console reporting delay — give it time to clear on its own rather than assuming a real bug.
- **Building small custom tools/widgets without deep coding skill (vibe-coding):** use an AI coding tool (Claude Code or Google Antigravity), prompt it in plain language for what the tool should do, review/adjust the generated code, host it on a separate server, then link/embed it into the main site rather than pasting raw code into the CMS.
- **GBP visibility troubleshooting checklist (used live on Maria's profile):** confirm regular posting, confirm images are geotagged to the service location, confirm service descriptions are present, confirm the whole profile is fully optimized (services, cities, categories) — then check all of it monthly since descriptions can silently vanish/get declined/get edited by the public.

## Rules / dos & don'ts

- GBP post image size: no exact required size, but recommended standard is **1,000 × 1,000** (square).
- Post to your Google Business Profile **at least once a week** under the Posts section — this signals to Google that the profile is actively maintained.
- Re-check your GBP business description and full profile info **at least once a month** — descriptions can be silently declined, publicly edited, or disappear "through no fault of your own."
- Start every GBP post description with the exact keyword you want that profile to rank for (example given: "SEO agency in Hamilton").
- GBP images should be geotagged to the location being served.
- Local business schema: main/service-area schema goes on the homepage only; each individual city/location page gets its own separate single-location schema; multiple physical locations (multiple GBPs) require multiple full schemas.
- Don't disallow blog, collections, or product paths in robots.txt — a common misconfiguration introduced by a third-party app/plugin, not the site owner; audit for this after any platform migration.
- Videos should always be hosted externally (e.g. YouTube) — never self-hosted directly on the site/WordPress.
- WordPress is recommended over Squarespace, Wix, and Shopify specifically for flexibility: unrestricted custom code placement, no plugin/add-on ceiling, ability to set up email lists and push notifications not available on the other platforms.
- Don't trust an SEO tool's automated word count at face value, especially against a competitor's — verify manually by copy-pasting visible content into a separate word counter.
- When you delay JavaScript for speed, always re-test both the speed number and full page functionality — delaying (not blocking) can still break something if load order matters.
- Never paste AI-generated ("vibe-coded") output directly into something like a SQL database manually — that's flagged as the one real way to break a site this way; otherwise the risk to a non-technical user is low.
- It's fine (not urgent to fix) if a flagged GSC URL only differs by http vs. https and isn't actually the live version — ignore it; only chase real www/protocol mismatches against the live site.

## Tradeoffs & nuance

- Deciding to fix a current template vs. switch to a new one is not a given — test speed on BOTH versions first rather than assuming a new/competitor-inspired template will automatically be faster.
- Not every "not indexed" flag in GSC is a real problem — many are template/dynamic pages or files "that wouldn't rank anyways"; separate real issues (blocked by robots, genuinely broken canonical) from background noise before treating a large not-indexed count as an emergency.
- "Alternate page with improper canonical tag" warnings are often a false alarm — the canonical may already point correctly to the right page, and the flagged URL is just a dynamic/parameterized duplicate (e.g., with a `?` appended); check the actual canonical target before assuming it's broken.
- Delaying JavaScript can help speed but load order matters — a resource loading late may break something else that depended on it; treat every delay change as something to A/B test, not a guaranteed-safe win.
- CDN/security layers can block legitimate SEO crawler bots as an unintended side effect of their protections — described as an active, unresolved problem ("for the last few weeks") rather than a solved one, with Cloudflare called out as the recurring culprit.
- Word-count tools are unreliable across page builders/CMS's because they can pick up hidden text, pop-ups, review widgets, and duplicated mobile content — don't chase exact word-count parity with a competitor using automated tools alone; verify by hand.
- Platform choice is a flexibility-vs-simplicity tradeoff: Squarespace/Wix/Shopify limit which plugins/customizations you can install; WordPress trades that simplicity for maximum flexibility — worth the migration specifically when a site owner already plans significant changes anyway, less clearly worth it otherwise.
- On platforms without server/code access (Wix, and Shopify to an extent), fixes that would be trivial via server settings elsewhere (forcing WebP, editing raw crawl rules) instead require workarounds — manual image re-upload, digging through theme files, or asking a platform's built-in AI assistant.
- A brand-new, keyword-rich-named Google Business Profile can visibly outrank an older, formally-named one almost immediately — suggesting exact-match naming can matter as much as, or more than, the full checklist of individual optimization tactics (posting cadence, geotagging, descriptions) applied to a profile with a generic name.
- AI vibe-coding tools (Claude Code, Google Antigravity) are pitched as accessible to non-technical users, but the output is expected to be reviewed/adjusted by someone with technical judgment before hosting, and hosted on a separate server rather than embedded directly into fragile parts of a site.
