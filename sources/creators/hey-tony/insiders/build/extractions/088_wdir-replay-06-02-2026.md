## Tactics & step-by-step how-to

- **Building your own free SEO tools with Claude Code, no coding knowledge required:** Matt describes prompting Claude Code with something like "I want to build a tool that crawls Reddit, based on a keyword or a topic that I type in, and tells me a bunch of questions people are asking about that topic, gives me keywords, some pain points, and analyzes the content/comments" — Claude Code built the entire tool from that description.
- **Live bug-fix demo:** when the Reddit tool errored ("AI analysis failed"), Matt pasted the error message into Claude Code and said only "my Reddit tool isn't working, it's saying AI analysis failed" — Claude Code diagnosed and patched it live on the call; tool worked immediately after restart. No manual debugging by Matt at all.
- **Reddit content-mining workflow (manual, no tool needed):** search Google with `site:reddit.com [keyword]` — Reddit's own on-site search is weak, but Google has indexed Reddit thoroughly, so this surfaces relevant threads reliably.
- **Turning one Reddit complaint into a full content batch (member's win):** find a recurring complaint/problem on Reddit → write a blog post answering it → repurpose into a LinkedIn post → repurpose into 12 separate Instagram posts, all from the single Reddit thread.
- **Keyword-to-content-type decision process (demoed live on Oliver's ayahuasca site):** (1) pull a natural-language question straight from the Reddit tool (e.g., "anyone's first-time experience at an ayahuasca retreat as a couple?"); (2) derive a short candidate keyword from it ("ayahuasca couples retreat"); (3) check that keyword's monthly search volume and keyword difficulty in Semrush; (4) judge search intent — transactional/buy-intent keywords ("ayahuasca couples retreat") become a **service page**, not a blog post; informational keywords ("how much is an ayahuasca retreat") become a **blog post**.
- **Updating old/underperforming blog posts instead of writing new ones:** if a post isn't ranking, don't write a fresh post on the same topic — diagnose and fix the existing one. Diagnostic checklist: is it too long? too short? doesn't include the target keyword enough times? doesn't actually answer the question right away?
- **Content depth for "cost/price" type queries:** cover the full range (low, mid, high end) and mention multiple relevant locations even if your business only operates in one — mirrors what top-ranking competitors already do for these terms.
- **Competitor-structure teardown for a target keyword:** pull up whoever ranks #1 for your target keyword, look at exactly what subtopics/H2s they cover (e.g., "what to look for in a reputable center," pricing by region, budget tiers) and make sure your own piece covers the same ground.
- **Site-audit troubleshooting (Alex's case):** a page ("meet the team," slug `/about`) was flagged "not found" and as a broken link despite being visible in the site's own sitemap and reachable by direct navigation — Matt couldn't diagnose it live and asked Alex to email a link to the site so his developer could look into the crawl issue directly.
- **Fixing a "link farm"-flagged domain (Daniela's case), two paths:** (A) stay on the domain — contact referring-domain owners to request removal of unwanted/spammy backlinks, then actively build new legitimate backlinks; or (B) if the domain has no real rankings/traffic to lose, register a similar new domain (e.g., add "savvy," change TLD) and migrate the site fresh rather than fight the existing domain's link profile.
- **Cleaning bad backlinks generally:** check Semrush → referring domains → identify low/zero authority-score or irrelevant-geo spam domains → contact those site owners and ask them to remove the link; treat this as normal maintenance every site needs periodically, not a crisis.
- **Disavowing links:** doable via Google Search Console (Matt navigated toward "Links" → "Security & Manual Actions" area on the call, thinking aloud through the console's own menu) or through Semrush if it's connected to your Search Console account.
- **Site relaunch after years offline (Will's theater-ticket site), backlink-preservation sequence:** (1) for backlinks you don't care about keeping, do a straight 301 redirect to the closest relevant current page; (2) for backlinks from high-value/authoritative sites (The Guardian, Wikipedia, Pinterest, niche press), consider rebuilding a page at the **same original URL** rather than redirecting — this passes more link authority through than a redirect does, especially valuable if the linking site might later clean up its own outbound links and remove ones that only point to a redirect; (3) launch, then run a press release announcing the relaunch to help kick-start momentum.
- **Deciding whether to keep old/legacy content when relaunching a site:** pull every existing piece of content and check three things — is it indexed? is it getting traffic? is it optimized? If the answer to all three is no (Matt: "which is like 99% of the time"), delete it. Google gives every site a crawl budget, and a majority-unindexed site is a bad signal.
- **Handling "sold out"/no-longer-available product pages (closed theater shows):** keep the page live if the show/product is still actively searched for, mark it sold out in visible copy, set inventory to 0 in schema markup, and add a "notify me if this returns" signup to capture future demand instead of deleting the page outright.
- **Fixing an over-optimized-for-design homepage (Oliver's ~100 H2 tags issue):** the site was designed for visual layout first with no SEO structure — Matt's fix direction was to collapse this down to a proper heading hierarchy built around one clear target keyword rather than a heading tag on every visual block.
- **Region/country keyword splitting for a multi-destination travel site (Anya's case):** don't lump culturally-understood-but-not-literal terms like "down under" into one page/keyword — Google doesn't know "down under" means Australia + New Zealand, so split those into two separate destination pages, each targeting its own country name as the primary keyword.
- **Per-destination page content requirements:** each country/destination page needs its own H1 built around the destination name (not generic travel copy), more than a single H2, and content that goes beyond textbook facts (e.g., "Botswana is a landlocked country in southern Africa") toward actual itinerary detail and real trip/traveler description — the textbook facts are already available elsewhere on Google.
- **Trust-building for a high-cost/high-perceived-risk niche (adventure/safety travel):** show real people who've actually done the trip (not stock-looking photography), show what the vehicle/accommodations actually look like, add video (social content is fine) of real travelers or the business owner, and move the "About"/personal bio higher up the page or into the main flow rather than burying it — frame the About section around the person ("Meet Anya") since people are buying from a person, not just a company.
- **Page layout fix:** add real side margins/whitespace so body content lives in a narrower center column instead of spanning the full page width edge-to-edge (Matt used HeyTony's own blog layout as the visual reference).
- **Not every page needs a target keyword:** "how it works" pages can loosely target a keyword variant if relevant; "About" pages generally should not be keyword-chased — they behave similarly to the homepage and aren't expected to rank independently.
- **Local SEO expansion strategy when already ranking well in a mid-size market (Adam's Mississauga/Toronto case):** rather than pouring more effort into out-competing a much bigger, much more contested market, build individual **service pages** (not just blog posts) for smaller nearby towns/markets with low or no visible search volume but essentially zero competition (examples given: Vaughan, King City, Stouffville).
- **Getting new local pages indexed faster:** link to each area/location service page directly from the homepage (an "areas we serve" section with real links), not only buried in the footer — footer-only links index slower.
- **Local page uniqueness rule:** every location page can share the same template/structure, but each page's actual content must be substantively unique — reference local landmarks and local specifics, not just a swapped city name.
- **Choosing a website platform/builder for an SEO-first rebuild (Martin's case):** WordPress-native builders (e.g., Bricks) are preferred over non-WordPress drag-and-drop platforms (e.g., ShowIt) because WordPress lets you directly manipulate SEO-relevant tags/settings; a non-WordPress framework with only its blog bolted onto WordPress requires extra manual workaround effort to control on-page SEO.
- **SEO plugin selection:** pick exactly one SEO plugin (Yoast, Rank Math, All in One SEO, or SEOPress are all acceptable/equivalent) and don't switch a client off whatever plugin they're already using just out of personal preference.
- **Testimonial-gathering ask (for Rank Week's March relaunch):** Matt asked members to post testimonials specifying business type, how long they'd been in business, whether they were skeptical SEO would work for them, and quantifiable results/outcome.

## Rules / dos & don'ts (keep every threshold, number, specific)

- If you're currently getting real traffic/rankings from a domain, **do not disavow links** — Matt has seen clients tank previously-strong rankings by going in and disavowing on their own initiative after the fact.
- Disavowing is more reasonable/lower-risk specifically when a domain has no real traffic or rankings to lose (Daniela's and Will's pre-launch situations).
- Spammy/zero-authority referring domains (random directories, foreign-TLD junk, adult sites) are normal for **every** website, including Matt's own (hey-tony.ca) — don't panic over their presence alone; the issue is volume/relevance, not that they exist at all.
- Content pruning rule: delete a page only if it fails all three checks — not indexed, not getting traffic, not optimized. Matt: "which is like 99% of the time" true for old/legacy content on a relaunching site.
- Exception to the pruning rule: keep sold-out/discontinued product pages if the underlying thing (e.g., a closed show) is still actively searched for — mark unavailable, set schema inventory to 0, offer a "notify if returns" signup rather than deleting.
- Don't chase a 100% score on any audit tool — a 90% health score is described as "fantastic," and some flagged items (e.g., duplicate H1 tags across blog **category** pages) don't matter because category pages don't typically rank anyway.
- SEO plugin traffic-light scores (Yoast green, Rank Math score, etc.) are not a proxy for real SEO performance — getting the plugin's own checklist to "green" is explicitly called out as not necessarily helping rankings at all.
- One target keyword per page — reaffirmed across multiple member cases (Oliver's, Anya's, Adam's).
- "About" pages should not be keyword-targeted; they behave like the homepage and aren't expected to independently rank.
- Category/blog-taxonomy pages are not expected to rank — don't worry about duplicate H1s there.
- Local/location pages: same structural template is fine, but content per page must be unique (local landmarks, local specifics) — do not just find-and-replace the city name.
- When redesigning/relaunching a site, preserve original URLs for pages with valuable existing backlinks (Guardian, Wikipedia, etc.) rather than defaulting to a straight redirect — a kept/rebuilt original URL passes more authority than a 301.
- Press release for a site relaunch: doesn't need to be "big news" — a simple "we're back, here's what we do" release is enough to help kick things off.
- Only one SEO plugin per site — don't run two, and don't swap a client's existing plugin just for personal preference.

## Tradeoffs & nuance

- **Fix vs. migrate a "link farm" domain:** worth cleaning up (contact site owners, build new links) only if there's real traffic/rankings at stake; if a domain has nothing to lose, registering a fresh similar domain and migrating is the simpler path.
- **Disavow is situational, not default:** actively harmful to a site that's already ranking/getting traffic (client anecdote of rankings dropping after a self-initiated disavow cleanup), but reasonable when there's no traffic on the line.
- **301 redirect vs. rebuilding at the original URL:** a straight redirect is faster but passes less authority than recreating content at the exact URL a high-value backlink already points to — worth the extra rebuild effort specifically for authoritative referring domains (Guardian, Wikipedia), not worth it for low-value links.
- **Delete-old-content rule has an exception:** legacy pages otherwise destined for deletion (unindexed, no traffic) should be kept if they serve ongoing buyer intent (a sold-out show people still search for) — handled via sold-out messaging, schema, and a notify signup rather than a blanket delete.
- **Answer the Public vs. the new Reddit tool:** not a replacement relationship — use both; when a seed keyword returns wrong-intent results (career questions instead of buyer questions), the fix is to try a more specific/longer-tail seed term, not to abandon the tool.
- **SEO plugin "score" vs. actual SEO:** a plugin's green/red checklist is a UX nudge, not a ranking signal — chasing it can waste time or even lead you to reject good keyword choices because the plugin doesn't recognize them.
- **Chasing a bigger market vs. defending/expanding a won one:** the "obvious" next step (Mississauga → Toronto) is framed as often the wrong move — smaller adjacent low-competition markets can be faster, easier wins than fighting for a much larger, much more contested keyword.
- **WordPress-native builder vs. easier drag-and-drop platform:** ShowIt is easier to use/update long-term but sacrifices direct SEO/tag control since it isn't WordPress-native; Bricks trades some ease-of-use for full technical control.
- **Audit-tool score chasing vs. real priorities:** a 90% health score is "fantastic" and further chasing (e.g., duplicate H1s on category pages) isn't worth the time since those pages were never going to rank anyway — knowing which flags to ignore requires domain knowledge the tool itself doesn't provide.
